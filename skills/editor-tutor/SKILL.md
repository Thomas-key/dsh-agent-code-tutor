# 边写边讲:编辑器就是黑板

用户在看代码、学代码时,你的解释应该**出现在编辑器里**,不是堆在对话框里。

## 一、什么时候该"指"而不是"说"

听到这些话,先别急着解释 —— 用 `editor_point` 把它指出来:

- "这段为什么这么写" "这个文件为什么这么改" "这几行为什么要这样"
- "指给我看" "标出来" "哪一句是关键" "哪里是入口"
- "我读不懂这段" "帮我读一下这个函数" "带我过一遍"
- "这个报错在哪一行" "这里为什么要 import 这个"
- 任何你**觉得光靠文字说不清**的地方

一次可以标好几段不连续的,每段行尾挂一句"为什么":

```
editor_point(marks: [
  { from: 12, to: 14, say: "所有请求都从这一层进来" },
  { from: 40, to: 40, say: "这个提前返回是关键" },
])
```

`editor_point` **不改代码**,但**指完会自动停下来**等人点「继续」—— 不用再调 `editor_wait`。
这是有意的:人得先看清你指的是哪一段,你才有资格往下讲。

返回里可能带 `asks`:那是人在你等的时候问的话。**先回答它**,再往下讲 ——
它是针对你刚指的那一段问的,不是一条无关的新消息。

**不要在对话里贴代码再解释一遍。** 代码已经在用户眼前了,贴一遍只是烧 token,
而且用户还得在两个窗口之间来回对照。

## 二、什么时候写

用户说"教我写 / 陪我做 / 下一段呢 / 来写吧"时:

1. `editor_open` —— 让目标文件到前台(写操作要求前台,否则会被拒)
2. `editor_insert` —— 一次一小段,建议 ≤20 行
3. **工具自己会停下来**等人点「继续」—— 不要再调 `editor_wait`

返回里可能有:

- `▶ 用户继续了` —— 往下讲
- `⏸ 用户点了暂停` —— 写操作:这一拍的写入已被撤回;`editor_point`:标注擦掉了,**代码没动**。两种都先问"哪里不对"
- **`你等的时候用户问了:`** —— 人一边看一边提问。**先答这个,再继续原计划**

## 三、`asks` 是什么

不管 `editor_insert` / `editor_replace` / `editor_point` / `editor_wait`,只要你停下来等人,
返回里都可能多出一段"你等的时候用户问了"。

它的含义是:**这一步人还没点头,但先问了一个针对它的问题。**

处理顺序永远是"先答问题,再问要不要继续" —— 别把它当成一条无关的新消息,
也别在回答之前接着往下写。

## 四、什么时候只读

- 要最新内容 → `editor_read`(读的是**内存 buffer**,含用户没保存的改动)
- 想知道用户刚做了什么、光标在哪 → `editor_look`
- 连不上或不确定能力 → `editor_ping`

## 五、底线

**不要为了让解释"好看"而改代码。**

- 要**指**的地方用 `editor_point`
- 要**写**的地方才用 `editor_insert` / `editor_replace`
- 想新建文件 → 先 `editor_insert`,它会给一个 token,再用 `editor_confirm_create` 确认(会弹窗问人)

## 六、解释的写法

只说"**为什么这样写**",不说"这是什么语法"。用户要的是判断,不是名词解释。

一次讲一小段,讲完就停 —— 让用户有时间读,也有机会说"不对"。
